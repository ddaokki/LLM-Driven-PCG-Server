### 발표 대본 (약 1분 30초)

백엔드는 이번에 두 가지를 구현했습니다. 대화에서 Zone JSON까지 이어지는 파이프라인과, 그 결과를 언리얼 계약대로 맞추는 보정·검증 엔진입니다.

흐름은 네 단계입니다. 언리얼에서 플레이어의 대화 내역을 받고, LLM 모듈의 vLLM에 JSON Schema를 강제해 Zone 후보를 받습니다. 서버가 후보를 보정·검증한 뒤 Zone JSON을 돌려주면 언리얼이 PCG로 월드를 생성합니다.

구현은 Node.js와 Express로 REST 서버를 만들었고, 세션 저장소인 Redis는 없어도 동작하도록 장애 허용을 넣었습니다. 제약은 아직 vLLM 서버가 없다는 점이었습니다. 그래서 같은 인터페이스로 동작하는 규칙 기반 해석기를 두어 GPU 없이도 "대화가 바뀌면 존이 바뀌는" 흐름을 시연할 수 있게 했습니다. 실제 vLLM이 붙으면 설정값 하나로 전환됩니다.

보정 엔진은 경로 교차, 시작-도착 거리, 구역 겹침, 전투 개수, 값 범위를 계약대로 복구하고, 같은 입력에 항상 같은 결과를 냅니다. 자동 테스트 98건과 무작위·적대 입력 2만 건에서 예외 없이 통과했습니다.

다만 현재 역할 분담은 이렇습니다. 지금 쓰는 LLM 모델이 소형이라 출력이 들쑥날쑥해서, LLM 모듈이 1차 보정을 하고 백엔드는 그 결과를 계약 기준으로 재검증하는 단계입니다. 앞서 LLM 파트에서 말씀드린 것처럼 이후에는 LLM 모듈의 보정 단계가 빠지고 백엔드가 보정·검증을 전담할 예정입니다. 그때를 위한 계획은 세 가지입니다. 첫째, 실제 vLLM 출력을 모아 회귀 테스트셋을 만들고 보정 규칙을 재조정합니다. 둘째, 대화의 난이도 의도, 예를 들어 "처음엔 험난하고 점점 쉬워진다" 같은 요청을 받아 그 곡선 형태를 보장합니다. 셋째, 보정 리포트를 언리얼에 넘겨 어떤 값이 왜 바뀌었는지 보이게 합니다.

### 예상 질문

- "LLM이 이미 보정하는데 왜 또 하나?" → LLM 모듈 보정은 생성 데모 앱 안에서 동작. 서비스 경로(백엔드→vLLM API)에는 없고, 규칙 폴백·수동 입력 경로도 백엔드만 지남. 백엔드는 계약의 최종 관문.
- "난이도를 왜 정렬하나?" → 현재는 안전한 기본값(상승). LLM이 읽은 의도를 받아 곡선을 보장하는 방식으로 전환 예정. 값 집합은 유지하고 배열만 바꿈.
- "멱등이 뭔가?" → 보정 결과를 다시 넣어도 바뀌지 않음. 출력이 규칙을 전부 만족한다는 증명이자 재전송·캐시 안전.
